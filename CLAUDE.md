# CLAUDE.md

Гоночная игра на pygame + pymunk, где машинка учится проходить трассу через
нейроэволюцию (`neat-python`). Подробное описание — в [README.md](README.md).

## Запуск — всегда из корня репозитория, через `-m`

```bash
python -m car_racer.neat_runner.main   # обучение NEAT (единственный игровой режим)
python -m helpers.draw_track           # конструктор трассы мышью
python -m car_racer.tracks.build_real_circuits    # оцифровывает Монцу/Имолу из реальных схем
```

`python -m car_racer.neat_runner.main` при старте поднимает ещё и браузерную
панель мониторинга/управления на `http://127.0.0.1:8080/` (порт настраивается
переменной окружения `RACE_DASHBOARD_PORT`) — см. `car_racer/dashboard/` ниже.
Панель полностью заменила почти все настройки, которые раньше жили в
pygame-панели справа от игрового поля; в самом окне игры остались только два
плавающих тоггла (сенсоры/геном).

Ручной (клавиатурный) режим вождения (`car_racer/runner/main.py`,
`SimpleCar`) убран по явному запросу пользователя - он не тестировался при
масштабных изменениях трасс/камеры (не вызывал `Screen.compute_fit_zoom()`,
не имел пана/зума, показывал только маленький угол трассы на выросших после
`PX_PER_METER` треках) и требовал держать `SimpleCar` синхронной копией
`PhyCar` (см. ниже) ради кода, который никто не запускал. `PhyCar` теперь
единственная модель машины в проекте.

`car_racer/tracks/track_builder.py` — библиотека для генерации по схеме
(`build_track`/`fit_to_screen`/`save_track_file`, см. ниже), у неё больше НЕТ
`__main__` (раньше генерировала `points_oval.txt`/`points_stadium_chicane.txt`
— первый пересобран отдельно под реальные метры, второй удалён — оставлять
исполняемый пример, воскрешающий их под старыми именами, было бы только
путаницей). `OVAL_SCHEMA`/`STADIUM_WITH_CHICANE_SCHEMA` внутри — просто
справочные примеры формата схемы, не генерируют файлы сами по себе.

Код использует относительные пути (`./assets/car.png`, `car_racer/tracks/...`)
и абсолютные импорты `from car_racer.xxx import ...` / `from helpers.xxx import ...`.
Запуск файла напрямую (`python car_racer/neat_runner/main.py`) или не из корня
репозитория сломает и то, и другое — только `-m` из корня.

## Окружение

venv в `.venv/`, зависимости в `requirements.txt` — версии актуальные на
момент написания (`Pillow`/`scikit-image`/`scipy` добавлены туда же —
раньше были не объявлены вовсе, хотя `car_racer/tracks/build_real_circuits.py`
их напрямую импортирует для оцифровки Имолы; `numpy` поднят до фактически
установленной 2.2.6, см. комментарий в `requirements.txt`). `pymunk` (7.x) и `neat-python` (2.0) в последних мажорных
релизах ломают обратную совместимость (у pymunk переписан `Vec2d` и другое
поведение `pygame_util`, у neat-python несовместимый формат чекпоинтов и
новые обязательные параметры конфига) — это проверено и учтено (см.
комментарии в `requirements.txt` и правки в `config-feedforward.txt`), но при
следующем мажорном апгрейде любой из зависимостей повторяй ту же процедуру:
проверяй changelog на breaking changes и прогоняй реальный тик игры (создание
`Screen`/`GameEnvironment`, `env.update()` в цикле) headless
(`SDL_VIDEODRIVER=dummy`) перед тем как менять версию в `requirements.txt`.
Чекпоинты обучения в `car_racer/checkpoints/` — расходный материал, их не
жалко терять при смене версии neat-python (несовместимы между мажорными
версиями) или в принципе когда они не нужны.

## Архитектура

- `car_racer/constants.py` — `PX_PER_METER = 20.0` (`METERS_PER_PX` — обратная
  величина) — единственная РЕАЛЬНАЯ калибровка px→метры в проекте (раньше её
  не было вообще, см. про `ENGINE_POWER_HP`/`CAR_MASS` ниже — те остаются
  УСЛОВНЫМИ этикетками, не калибровкой длины; `GRIP_ACCEL_PER_G` — исключение,
  см. `physic_car.py` ниже, теперь честно выведен из этой самой калибровки).
  Привязана к
  спрайту тренировочной машины (`PhyCar(..., car_size=(15, 35), ...)` в
  `neat_runner/game_instatnse.py`) — 15px ширины = 0.75 м, 35px длины = 1.75 м
  (правдоподобный прокатный картинг), отсюда `20.0`. Используется ТОЛЬКО для
  геометрии/визуализации (масштаб трасс, масштабная линейка — см.
  `Screen.draw_scale_bar` ниже; той же конвертацией `ui_panel.py` переводит
  "Max Distance" в статистике из игровых px в метры при выводе - сам
  `max_distance` в `neat_runner/main.py` остаётся в px, делится на
  `PX_PER_METER` только в строке для отображения) — физика машины (`MAX_SPEED`, `GRIP_ACCEL`,
  `ENGINE_POWER_HP`, `ROTATE_POWER` и т.п. в `physic_car.py`) в игровых
  px/с, px/с² не тронута и не привязана к этому масштабу.
- `car_racer/cars/{abs_car,physic_car}.py` — модель машины. `PhyCar` (физика
  pymunk) — единственная модель в проекте, используется и в обучении, и
  раньше использовалась бы в ручном режиме, если бы он существовал.
  `SimpleCar` (упрощённая кинематика, без модели сцепления ниже) и весь
  ручной (клавиатурный) режим вождения (`car_racer/runner/main.py`) убраны
  по явному запросу пользователя — `SimpleCar` была 1:1 дублирующей копией
  `PhyCar` (`get_inputs_for_network`, `check_collision_with_*`), которую
  приходилось синхронно поддерживать (см. историю правок сенсоров/компаса в
  этом файле) при том, что реально запускался только ручной режим, который
  сам по себе был неисправен на актуальных трассах (не звал
  `Screen.compute_fit_zoom()`, не имел пана/зума — показывал только маленький
  угол трассы после перехода на `PX_PER_METER`). Если понадобится
  вернуть ручное управление — делать его через `PhyCar` (тот же
  `throttle()`/`turn()`/`damping()` интерфейс, которым уже пользуется NEAT),
  а не воскрешать отдельный класс.
  `PhyCar.throttle()`/`turn()` не мутируют тело напрямую — они только
  запоминают запрошенное действие (`_pending_throttle_power`/`_pending_turn_power`
  + флаги `_has_pending_*`), а `update()` применяет их СОВМЕСТНО через
  `_apply_controls()`.

  **Руль — кинематика велосипеда, а не прямая угловая скорость.** Раньше
  `turn()` напрямую задавал ЦЕЛЕВУЮ угловую скорость (плюс ручная поправка
  `SPEED_EFFECT` на скорость и штраф за отсутствие дифференциала `NO_DIFF_*`).
  Теперь `turn()` задаёт ЦЕЛЬ для угла передних колёс `δ` (`self.steering_angle`,
  ограничен `MAX_STEERING_ANGLE`≈0.6 рад/34°, задаёт минимальный радиус
  поворота), сам угол поворачивается с конечной скоростью `STEERING_RATE`
  (руль нельзя дёрнуть мгновенно), а угловая скорость выводится из скорости и
  δ по формуле велосипеда: `ω = v / WHEELBASE * tan(δ)` (`WHEELBASE`≈30px/1.5м).
  Из этого САМО следует то, что раньше имитировалось вручную: машина не
  вращается на месте (ω→0 при v→0, штраф `NO_DIFF_*` больше не нужен), а
  поперечное ускорение `a = v·ω` естественно ограничивается кругом трения
  (см. ниже) — на высокой скорости руль сам по себе "слабее".

  **Снос (slip angle) — вектор скорости не мгновенно следует за курсом.**
  Раньше `body.velocity` каждый тик жёстко проецировалась на `body.angle` —
  машина ехала "по рельсам", бокового скольжения не существовало в принципе, а
  снос/занос/скраб имитировались отдельными ручными "киками"
  (`UNDERSTEER_*`/`OVERSTEER_*`/`STEER_SCRUB_COEFF`, реагировавшими на
  `|Δ(throttle_power/turn_power)|` между тиками через `_prev_throttle_power`/
  `_prev_turn_power`) — все они убраны как заплатки поверх модели без
  собственного скольжения. Теперь у машины есть `self.velocity_heading`
  (направление вектора скорости) ОТДЕЛЬНОЕ от `self.body.angle` (курс шасси) —
  `velocity_heading` "догоняет" курс с конечной скоростью
  (`align_rate = SLIP_ALIGN_GAIN / (1 + v * SLIP_SPEED_FACTOR)`, т.е. чем выше
  скорость, тем медленнее прилипание — инерция), и именно вдоль
  `velocity_heading` (не `body.angle`) выставляется `self.body.velocity` в
  конце `_apply_controls()`. На высокой скорости или при резком руле машина
  заметно "плывёт" носом внутрь поворота, как настоящий картинг на пределе
  сцепления, а не мгновенно едет туда, куда повёрнут корпус.

  **Круг трения (`GRIP_ACCEL`) — теперь честная калибровка, а не этикетка.**
  Доступное сцепление шин по-прежнему ограничивает СУММУ продольного
  (разгон/торможение) и поперечного (`a = v·ω` из руля выше) ускорения — жать
  газ в пол и резко поворачивать одновременно физически нельзя, комбинация
  ужимается пропорционально общему бюджету (круг, не отдельные лимиты для
  каждой оси). Раньше `GRIP_ACCEL=2000 px/s²` было ПРОИЗВОЛЬНОЙ величиной,
  подобранной под старую лаг-модель разгона, а `GRIP_ACCEL_PER_G` было
  ОБРАТНО выведено из неё (`GRIP_ACCEL/1.5`) просто чтобы ПОКАЗАТЬ слайдеру
  "1.5g" — не независимая калибровка px→метры. Теперь наоборот:
  `GRIP_ACCEL_PER_G = 9.81 * PX_PER_METER` (честный 1g через единственную
  реальную калибровку проекта), `GRIP_ACCEL = 1.5 * GRIP_ACCEL_PER_G` —
  получилось **294.3 px/s², то есть почти в 7 раз МЕНЬШЕ старого значения**.
  Это не занижение — 1.5g физически правдоподобен для картинга на асфальте
  (проверено: разгон с места до `MAX_SPEED`=400px/с занимает ~1с, при полном
  руле на скорости машина сама сходится к равновесному виражу — устойчиво,
  без расходящихся колебаний), но это ЗАМЕТНО другое ощущение вождения и
  фитнес-сигнал, чем раньше, — даже сильнее, чем при первом введении круга
  трения (см. абзац про `_apply_controls` выше в истории). Старые чекпоинты
  обучения технически загрузятся (структура генома не менялась), но были
  натренированы под другую динамику разгона/поворота — на практике геномы,
  обученные до этого изменения, после него быстро теряют накопленный фитнес и
  массово вылетают почти сразу же после возобновления обучения.

  **`_desired_speed` — двигательный потолок ускорения, а не скорость
  "подтягивания" к цели.** Побочный эффект пересчёта `GRIP_ACCEL` выше: пока
  разгон моделировался как `new_speed = current + (target - current) *
  effective_rate` (`effective_rate` зависел от мощности/массы), требуемое на
  этот тик ускорение было пропорционально ВСЕЙ разнице до целевой скорости —
  при старте с места (или после сильного торможения) оно почти при ЛЮБОЙ
  настройке мощности улетало далеко за новый (пониженный) `GRIP_ACCEL` и
  обрезалось кругом трения в `_apply_controls` до ОДНОГО и того же значения
  - "Мощность (л.с.)" на практике переставала на что-либо влиять уже
  начиная с ~5 л.с. (при референсных 15; проверено эмпирически - разгон с
  места при HP=5..1000 давал идентичные кривые скорости). Исправлено явным
  потолком: `max_accel = GRIP_ACCEL * power_ratio * mass_ratio`, дальше как
  раньше проходит через тот же круг трения. На референсных мощности/массе
  (`power_ratio=mass_ratio=1`) потолок РОВНО равен `GRIP_ACCEL` - разгон при
  дефолтных 15 л.с. не изменился (проверено: идентичная кривая скорости, как
  и до этого фикса). Ниже референса потолок ниже `GRIP_ACCEL` - мощность
  теперь реально ограничивает разгон раньше сцепления. Выше референса потолок
  выше `GRIP_ACCEL` - обрезает уже круг трения, как и должно быть (двигатель
  не может "перебить" сцепление шин с асфальтом), так что мощность и ДО, и
  ПОСЛЕ фикса перестаёт что-либо менять выше некоторого порога - просто
  теперь этот порог совпадает с референсной мощностью/сцеплением, а не
  наступает почти сразу после минимума диапазона. Старая константа
  `ACCELERATION_RATE` (лаг-модели) убрана целиком - не путай новый
  `max_accel` (потолок, px/s²) с ней, это разные по смыслу величины.
  `car_racer/trajectory/optimal_line.py::vehicle_params_from_physic_car()`
  синхронно переведён на ту же формулу (раньше реплицировал старую
  лаг-модель через `physic_car.ACCELERATION_RATE` - сломался бы без этого).
  `GRIP_ACCEL`, `CAR_MASS`, `ENGINE_POWER_HP` — модульные переменные (не
  константы в привычном смысле): браузерная панель (`car_racer/dashboard/`,
  поля "Сцепление (g)"/"Вес (кг)"/"Мощность (л.с.)") мутирует их через команды
  `set_grip`/`set_mass`/`set_power`, обрабатываемые в
  `neat_runner/main.py::_handle_dashboard_commands` (`physic_car.<ИМЯ> = ...`)
  — новое значение подхватывают только НОВЫЕ машины (следующая группа), у уже
  бегущих ничего не меняется на лету. `CAR_MASS`/`ENGINE_POWER_HP` (в отличие
  от `GRIP_ACCEL_PER_G` выше) остаются калибровочными ЭТИКЕТКАМИ для полей
  панели через `REFERENCE_MASS_KG`/`REFERENCE_POWER_HP` (см. комментарии в
  `physic_car.py`) — независимой калибровки массы/мощности в проекте как не
  было, так и нет.
  `check_collision_with_track` считает расстояние до стен векторизованно
  (`helpers.calculate.min_distance_to_segments`, те же `track_segments_start/end`,
  что и сенсоры) — раньше был Python-цикл с `pygame.Rect.clipline()` по
  каждому сегменту + повторное чтение `body.position` внутри цикла, что после
  удаления `shapely` из сенсоров стало ~74% времени тика (профилировано);
  сейчас общий прирост на этом месте — ~5.5x. Перед этой проверкой — ВТОРОЙ,
  грубый backstop-барьер: позиция машины сравнивается с `screen.world_bounds`
  (`(min_x, min_y, max_x, max_y)`, см. `Screen._recompute_world_bounds`) —
  bounding box ТЕКУЩЕЙ трассы (`track_outer`+`track_inner`) плюс отступ
  `WORLD_BOUNDS_MARGIN`=200px. Раньше здесь были фиксированные
  `screen.screen_width/screen.screen_height` (2000x1200) — перестало
  работать, когда трасса стала физически больше рендер-канваса (см.
  `points_xti_winter.txt` ниже, bbox ~6400x3250px) — со старой проверкой
  машины на дальней части такой трассы ложно считались бы выехавшими за
  пределы. `world_bounds` — ЧИСТО числовой прямоугольник (4 float на
  сравнение позиции), НЕ связан с размером `self.win`/`Camera`-viewport —
  рендер-канвас (~2000x1200) не меняется вместе с размером мира, в этом и
  смысл `Camera` (пан+зум показывает произвольно большой мир на канвасе
  фиксированного размера). Это ВТОРИЧНЫЙ барьер ("машина где-то ДАЛЕКО за
  пределами трассы") — основной детектор "разбился о стену" остаётся
  `min_distance_to_segments` и не связан с `world_bounds` вообще.
- `car_racer/neat_runner/game_instatnse.py` (да, опечатка в имени файла — так
  сложилось исторически, менять не нужно без явной причины, на неё много
  ссылок) — одна "игровая сессия" генома, разделена на `decide()` (сенсоры →
  сеть → газ/руль, физику не шагает) и `resolve()` (вызывается ПОСЛЕ шага
  физики: бухгалтерия машины + проверка столкновений/чекпоинтов/фитнеса).
  Разделение существует ради общего `pymunk.Space` на группу — см. ниже.
  `update()` = `decide()+resolve()` одним вызовом, для одиночного
  использования без общего Space (тогда физику шагает сам `car.update()`).
  `resolve()` при столкновении со стеной сразу `return`ает (после
  `self.active = False`) — раньше проверки чекпоинта/финиша шли следом в
  ТОМ ЖЕ вызове без переповторной проверки `active`, так что геном, который
  разбивался ровно в момент пересечения чекпоинта/финишной линии, всё равно
  получал за этот тик +1 фитнеса (или +5 и бонус за круг) — авария и
  прохождение чекпоинта в один и тот же тик не должны засчитываться оба.
  Бонус за круг — `60 / lap_time` (было `20 /`) — со старым коэффициентом
  бонус за реалистичный круг (~20-60с) составлял всего ~0.3-1.0, почти не
  отличая быструю езду от медленной на фоне остальных источников фитнеса
  (+1 за чекпоинт); `60/` даёт ~3.0 за 20-секундный круг — заметный вес,
  особенно на трассах с малым числом чекпоинтов после прореживания
  (`points.txt`=5), где сумма чекпоинтных +1 за круг сама по себе невелика.
  Инпуты сети — 10 нормализованных значений (угол/скорость + "компас" на
  следующий чекпоинт + 7 дистанций лучей-сенсоров), выходы — газ и руль
  подаются в машину напрямую, без порога/dead zone. Компас (см.
  `PhyCar._heading_error_to_next_checkpoint`) добавлен
  после того, как долгий прогон (56 поколений, лучший фитнес в популяции всё
  время держался ~1.3-1.7, среднее не росло, видов — 1 всё время) показал,
  что чисто реактивных лучей-дальномеров недостаточно: без сигнала "куда
  едет трасса" сеть не может надёжно выбрать нужный поворот там, где стены
  не подсказывают его достаточно рано. Компас указывает НЕ точно на середину
  следующего чекпоинта, а на взвешенную смесь (`CHECKPOINT_LOOKAHEAD_WEIGHT`
  в `physic_car.py`, сейчас 0.6/0.4) середины следующего чекпоинта и того,
  что идёт ЗА ним (`_gate_midpoint`) — точное прицеливание в один чекпоинт
  при плотных чекпоинтах (см. `_densify_checkpoints`) давало заметный
  зигзаг вокруг сглаженной трассы (пользователь принял это за "тягу к
  идеальной линии" — на деле `ideal_line` в фитнес/сеть вообще не подключена,
  только визуальный оверлей и статистика "Ideal lap" в панели). Полностью
  убирать компас не стали — риск вернуть застревание обучения, которое он и
  решал (см. абзац выше); сглаживание цели даёт направляющий сигнал без
  дословного "от точки к точке". У САМОГО финиша (`next_checkpoint_index ==
  len(checkpoints)`) раньше lookahead-блендинг вообще не применялся (условие
  `if idx < len(checkpoints):` было ложным) — компас указывал ТОЧНО на
  середину финишной линии без сглаживания, в отличие от любого другого
  чекпоинта, что давало нестабильный, резко меняющийся сигнал курса прямо
  перед финишем. Теперь на финише lookahead берёт ПЕРВЫЙ чекпоинт НОВОГО
  круга (`_gate_midpoint(0)`) — сглаживание работает единообразно везде,
  включая переход через финиш. Меняет число входов сети
  (`num_inputs` в `config-feedforward.txt`) — старые чекпоинты обучения
  структурно несовместимы, но они и так расходный материал (см. раздел
  "Окружение"). Таймаут и время круга считаются в тиках (`ticks_elapsed`,
  `TICK_RATE` в `car_racer/constants.py`), не в `time.time()` — важно не
  откатывать на wall-clock, иначе сломается турбо-режим (см. ниже).
- `car_racer/neat_runner/main.py` — цикл эволюции: геномы группами по
  `GROUP_SIZE`, чекпоинт всей популяции сохраняется через `pickle` после
  каждого поколения (не через встроенный `neat.Checkpointer`). Все машины
  группы делят один `pymunk.Space` (создаётся заново на каждую попытку
  группы) — порядок в тик-цикле строго `decide() для всех → space.step() один
  раз → resolve() для всех`; не вызывай `env.update()` напрямую в групповом
  цикле, это заново создаст собственный Space внутри PhyCar и сломает шаринг.

  раз (модульная переменная `screen`, лениво инициализируется при первом
  вызове `eval_genomes`) и переиспользуются между поколениями — не
  пересоздавай их каждый вызов, иначе будет пересоздаваться окно. Пауза/
  Unlimited FPS/Camera Follow/zoom/Track Lines больше НЕ состояние панели
  (панель теперь хранит только `show_sensors`/`show_genome`, см. `UIPanel`
  ниже) — это простые модульные переменные (`paused`, `unlimited_fps`,
  `camera_follow`, `zoom`, `show_track_lines`), которые правит браузерная
  панель через `_handle_dashboard_commands` (см. ниже), так что их состояние
  и без пересоздания `screen`/`panel` продолжало бы жить между поколениями.
  `p` (текущий `neat.Population`) — тоже модульная переменная, задаётся
  только в `if __name__ == "__main__":`, но читается в `eval_genomes()`
  (`save_checkpoint(p, generation)`) — там теперь есть `global p` в списке
  globals в начале функции: без него это работало (Python резолвит свободную
  переменную функции в область видимости МОДУЛЯ на момент вызова, а `p` к
  первому вызову `eval_genomes` из `p.run(...)` уже существует), но неявно и
  легко сломать, добавив в функцию локальное присваивание `p = ...`.

  **Браузерная панель (`car_racer/dashboard/`, см. отдельный пункт ниже)
  заменила почти всю pygame-панель.** `_handle_dashboard_commands(panel, cfg)`
  вызывается КАЖДЫЙ тик (не только при рендере — как и синхронизация
  `screen.show_sensors`/`show_track_lines` ниже, команда может прийти в любой
  момент, а не только в кадре с отрисовкой) и вычерпывает ВСЮ очередь команд
  из браузера за один вызов (`while True: cmd = dashboard.next_command(); if
  cmd is None: return`) — а не одну команду за тик, иначе при активном
  тюнинге слайдеров в браузере команды копились бы быстрее, чем
  обрабатываются. Числовые команды (`set_group_size`/`set_max_visible`/
  `set_pop_size`/`set_fps`/`set_grip`/`set_mass`/`set_power`/`set_zoom`)
  зажимаются в те же границы, что раньше проверял `TextField`/`Slider` самой
  панели (см. `_clamp_int`/`_clamp_float` внутри), включая каскад
  `GROUP_SIZE`↔`MAX_VISIBLE`↔`pop_size` (уменьшение любого из них подрезает
  зависимые, как раньше `UIPanel._rebind_max_visible_bound`). `restart_group`
  не выполняется сразу (ставит `_pending_restart_group = True`, разбирается
  в начале следующей итерации тик-цикла — команда может прийти в момент,
  когда `environments` ещё не существуют), `restart_training` поднимает
  `RestartTrainingRequested` СРАЗУ (у браузера свой `confirm()`, повторное
  подтверждение через 3 секунды, которое раньше делала кнопка панели, не
  нужно). В обратную сторону: `eval_genomes` раз в `DASHBOARD_SYNC_INTERVAL`
  (1.0с РЕАЛЬНОГО времени, не тиков — троттлится явно, а не через
  `should_render`, чтобы живой снимок продолжал обновляться и в турбо-режиме
  без отрисовки) собирает снимок статистики/настроек и геном лидера
  (`dashboard.serialize_genome`, вызывается БЕЗУСЛОВНО — браузер сам решает,
  показывать сеть или нет, в отличие от `panel.show_genome`, который
  гейтит ТОЛЬКО оверлей сети на самом игровом холсте, см. `UIPanel` ниже) и
  кладёт его в `dashboard.set_current(...)`; в конце `eval_genomes`
  (`dashboard.record_generation(...)`) добавляет в историю по поколениям
  (фитнес mean/max/min, размеры видов и т.п. — рисуется графиками в браузере).
  Любое необработанное исключение в `p.run(...)` (`__main__`, за пределами
  `RestartTrainingRequested`) сохраняет полный traceback в
  `car_racer/config/error.log` ПЕРЕД тем, как перевыбросить — этот файл ещё
  не в `.gitignore` (как `user_settings.json`/чекпоинты, см. `settings_store.py`
  ниже) и должен туда попасть.
  Ручное панорамирование камеры (drag ЛКМ по игровому полю, как на карте) —
  модульные `_camera_drag_active`/`_camera_drag_last_pos`/`_camera_manual_pan`,
  обрабатывается в том же `for event in pygame.event.get():`, что и
  `VIDEORESIZE`/клики панели (событие уже переведено в логические координаты
  холста через `screen.window_to_logical` — переиспользует то же
  преобразование, что и клики по панели). `MOUSEBUTTONDOWN`, не "съеденный"
  `panel.handle_event`, начинает драг — раньше здесь ещё было условие
  `event.pos[0] < screen.screen_width` (не начинать драг над панелью справа),
  но с переездом почти всей панели в браузер (`car_racer/dashboard/`, см.
  ниже) игра теперь рисуется НА ВЕСЬ логический холст (см. `Camera`/
  `compute_fit_zoom` в `screen.py` ниже), а от старой pygame-панели остались
  только два плавающих тоггла в углу — они сами съедают клик по себе
  (`consumed`), отдельная зона-исключение по x-координате больше не нужна.
  `MOUSEMOTION` двигает `camera.center` на дельту мыши,
  делённую на `camera.zoom`, в СЕТЕВОМ направлении (карта едет ВМЕСТЕ с
  курсором). Независимо от Camera Follow, но координируется с ним:
  `_camera_drag_active` (True только пока зажата ЛКМ) подавляет
  `camera.follow(...)` в рендер-блоке на время самого драга — иначе follow
  затирал бы драг в тот же кадр; отпустили ЛКМ — follow как обычно продолжает
  центрировать камеру на лидере со следующего кадра (драг "временно
  перекрывает" follow, а не отключает его). `_camera_manual_pan` (True после
  ПЕРВОГО же драга, не сбрасывается по отпусканию ЛКМ) подавляет
  `center_on_field(...)` в режиме "Camera Follow выключен" — без этого ручной
  пан отменялся бы на следующем же отрисованном кадре (`center_on_field`
  вызывается там каждый кадр). Оба флага сбрасываются при смене трассы
  (команда `set_track` из браузерной панели, см. `_handle_dashboard_commands`
  в `car_racer/dashboard/` ниже — раньше это делал `panel.consume_track_change()`)
  — координаты новой трассы не связаны со старой панорамой.
  Зум колесом мыши — `MOUSEWHEEL` в том же цикле событий (только если не
  "съеден" панелью): умножает МОДУЛЬНУЮ переменную `zoom` на `1.15**event.y`
  (мультипликативный шаг — одинаково заметен и у минимального, и у
  максимального zoom), явно зажимает результат в `[MIN_ZOOM, MAX_ZOOM]`
  (`car_racer/screen/camera.py`). Раньше зум был полем `panel.zoom`,
  прокидывался через `panel.sync_initial_values(zoom=...)` (нужно было
  зажимать явно здесь, т.к. сам `sync_initial_values` зажимал только
  `zoom_slider.value`, не `panel.zoom`) — теперь `zoom` (как `paused`/
  `unlimited_fps`/`camera_follow`/`show_track_lines`) простая модульная
  переменная, читается напрямую в `screen.camera.zoom = zoom` в рендер-блоке
  и синхронизируется с браузерной панелью в обе стороны: `_handle_dashboard_commands`
  пишет её по команде `set_zoom` (слайдер в браузере), а `eval_genomes`
  периодически шлёт её обратно в `dashboard.set_current(...)` (см.
  `DASHBOARD_SYNC_INTERVAL` ниже), чтобы открытая вкладка браузера видела
  зум, изменённый колесом мыши в самой игре, и наоборот. Явный кламп в
  `[MIN_ZOOM, MAX_ZOOM]` по-прежнему нужен и для колеса мыши, и для команды
  `set_zoom` (`_clamp_float(value, MIN_ZOOM, MAX_ZOOM, 4)`) — иначе
  многократный скролл/резкое значение из браузера увели бы zoom за пределы,
  которые слайдер и так не должен позволять достичь.
  Активен над всем игровым полем — с переездом панели в браузер отдельной
  зоны-исключения по позиции курсора для колеса мыши больше нет (см. про
  панорамирование выше); прокрутка ровно над двумя плавающими тогглами в
  углу тоже зумит камеру — мелкая, осознанно не устранённая шероховатость.
  Автоматический "показать всю трассу" зум — `Screen.compute_fit_zoom()`
  подбирает zoom, при котором bounding box трассы (`_track_bbox_size`, см.
  `_recompute_world_bounds`) занимает `fill_fraction`=92% ВСЕГО логического
  холста (`logical_width x logical_height` — раньше было `screen_width x
  screen_height`, т.е. игровое поле БЕЗ панели; теперь игра рисуется на весь
  холст, см. `screen.py` ниже, и панели, которая раньше занимала под себя
  отдельную колонку, больше нет), зажат в `[MIN_ZOOM, MAX_ZOOM]`.
  `neat_runner/main.py` применяет его как стартовый zoom при первом создании
  `screen` И при каждой смене трассы (команда `set_track` из браузера, см.
  `car_racer/dashboard/` ниже) — ИГНОРИРУЯ сохранённый в `user_settings.json`
  zoom (см. `settings_store.py` выше): при открытии окна трасса должна сразу
  заполнять экран, а не восстанавливать zoom прошлой сессии, подобранный под
  трассу совсем другого реального размера (диапазон между
  `points_oval_half_mile.txt` и `points_monza.txt` теперь огромный, см.
  `PX_PER_METER` выше).
  Лидер группы (`group_best_env`, к нему цепляется камера при Camera
  Follow — см. `camera_follow` ниже, и на него ВСЕГДА, независимо от
  Camera Follow, опираются путь/подпись дистанции в рендер-блоке) forced в
  `car.visible = True` сразу после пересчёта каждый тик — иначе машина,
  реально ставшая лидером, но созданная с индексом ЗА пределами
  `MAX_VISIBLE` (видимость назначается один раз по индексу внутри группы при
  создании `GameEnvironment`, см. ниже, и никак не связана с тем, кто
  реально лидирует прямо сейчас), рисовалась бы как невидимая
  (`PhyCar.draw()` выходит по `visible=False`) именно в тот момент, когда
  камера/путь/подпись уже на неё указывают.
- `car_racer/screen/screen.py` — окно/отрисовка трассы/визуализация сети.
  `self.screen_width/self.screen_height` = размер окна (window_size), а
  `self.logical_width = screen_width + panel_width` — раньше это было "игровое
  поле + отдельная непрозрачная колонка панели справа", и `Camera`
  сознательно смотрела только на `screen_width x screen_height` (панель вне
  её зоны ответственности). Теперь, когда почти вся панель уехала в браузер
  (`car_racer/dashboard/`, см. ниже) и в самой игре остались только два
  плавающих полупрозрачных тоггла (`UIPanel`, см. ниже), игра рисуется НА
  ВЕСЬ логический холст: `self.camera = Camera(self.logical_width,
  self.logical_height)` (было `Camera(screen_width, screen_height)`),
  `_build_grass_texture`/`_draw_track_fill`/`compute_fit_zoom` тоже переведены
  на `logical_width x logical_height` (см. ниже) — трасса теперь визуально
  простирается под старую "зону панели" тоже, а не останавливается на
  границе `screen_width`. `UIPanel` при этом по-прежнему создаётся с
  `field_width=self.screen_width` и своим `panel_width` — то есть её
  прямоугольник (`x` от `screen_width` до `logical_width`) занимает ровно
  правую полосу ВИДИМОГО (теперь на весь холст) игрового поля, а не
  отдельную область за его пределами — отсюда "кнопки плавают поверх игры".
  `screen.load_track(filename)`
  переключает трассу на лету (используется браузерной панелью) — оба пути пересчитывают
  `track_segments_start/end` (numpy-кэш границ трассы для `cast_ray`) И
  `screen.world_bounds`/`screen.track_center` (`_recompute_world_bounds`) —
  не забывай вызывать оба пересчёта при любом другом способе поменять
  `track_outer/track_inner`. `track_center` — центр bounding box трассы (БЕЗ
  отступа) — нужен камере в режиме "показать весь трек" (см. `camera.py`
  ниже); раньше для этого использовался `(viewport_width/2, viewport_height/2)`,
  что совпадало с реальным центром трассы только пока все трассы были
  нарисованы внутри той же коробки, что и viewport (~2000x1200) — для трасс
  крупнее viewport'а (`points_xti_winter.txt`) это совпадение больше не
  работает.
  `Screen.draw_scale_bar()` — масштабная линейка google-maps-стиля в левом
  нижнем углу ИГРОВОГО ПОЛЯ (не в UI-панели справа — свойство камеры/карты, а
  не панели управления): брусок с засечками + подпись "N m"/"N km". Каждый
  кадр подбирает "круглое" число метров из ряда 1/2/5/10/20/50 м... такое,
  что его экранная длина при ТЕКУЩЕМ `camera.zoom` ближе всего к
  `SCALE_BAR_TARGET_PX`=110px — живо реагирует на слайдер Zoom без доп.
  действий. Перевод метры→экран идёт в два шага, по общей конвенции модуля:
  метры→мировые px (`* PX_PER_METER`, единственная калибровка px→метры в
  проекте) → экранные px (`camera.scale_length`, учитывает zoom). Вызывается
  из `neat_runner/main.py` рядом с `draw_track()`.
  `Screen.draw_track()` — раньше рисовал только контурные polyline outer/inner
  на сплошном чёрном (`self.win.fill(BLACK)`), полотно между ними и всё
  снаружи не заливались вовсе — выглядело пусто/безжизненно, особенно на
  крупных реальных трассах. Теперь: (1) фон снаружи — закэшированная один раз
  (`_build_grass_texture`, лениво при первом кадре) слегка "мятая" зелёная
  текстура (`GRASS_GREEN` + numpy-шум по блокам `GRASS_NOISE_SCALE`px,
  растянутый `smoothscale` до размера ВСЕГО логического холста —
  `logical_width x logical_height`, было `screen_width x screen_height` до
  переезда панели в браузер, см. начало этого пункта) — просто блитится каждый
  кадр В ЭКРАННЫХ координатах (НЕ едет с камерой при пане/зуме — осознанный
  компромисс простоты/производительности, это фон, не часть трассы);
  (2) само полотно (кольцо между outer/inner) — тёмно-серый `ASPHALT_COLOR`
  из ОТДЕЛЬНОЙ закэшированной текстуры В МИРОВЫХ координатах
  (`_build_track_fill_texture`/`_draw_track_fill`) — залить `pygame.draw.polygon`
  по ПОЛНЫМ outer/inner В ЭКРАННЫХ координатах КАЖДЫЙ КАДР стоило ~18ms/кадр
  на `points_monza.txt` (~9700 точек полотна, полигон в pygame стоит от числа
  вершин) — вместо этого полигон заливается ОДИН РАЗ в свою текстуру
  (пониженное разрешение, `TRACK_FILL_CACHE_MAX_DIM`=2048px по большей
  стороне bbox трассы), а каждый кадр эта готовая Surface просто
  масштабируется (`pygame.transform.scale`) под текущий `cam.zoom` и блитится
  в `cam.world_to_screen(origin)` — корректно ТОЛЬКО потому что `Camera` строго
  аффинна (scale+translate, без поворота, см. `camera.py`), так что
  "перемасштабировать готовую картинку" эквивалентно "перерисовать полигон
  под новую камеру". Кэш текстуры инвалидируется в `load_track()` (новая
  трасса — новый bbox/полигон). ВАЖНО: имя поля
  `track_outer` НЕ гарантирует, что этот контур геометрически больше
  `track_inner` (на `points_oval_half_mile.txt` наоборот) — `_build_track_fill_texture`
  сравнивает площади (`_polygon_area`, шоеласа) и большим контуром всегда
  заливает АСФАЛЬТ первым, меньшим — "дырку" (цветом фона, БЕЗ шума текстуры —
  видимый шов почти не заметен, сразу перекрывается чёткой контурной линией
  outer/inner, рисуемой отдельно по полным координатам); залить не глядя по
  порядку полей — типичный способ получить полностью невидимое полотно.

  `_draw_track_fill` (масштабирование текстуры под камеру) раньше
  масштабировало ВСЮ текстуру целиком под `cam.zoom`, с отдельным кэшем
  РЕЗУЛЬТАТА `transform.scale` по последнему использованному `cam.zoom`
  (`_track_fill_scaled_cache`, теперь убран) — это было реальным багом:
  вылет (`MemoryError`/SDL out of memory) при приближении камеры на
  `points_monza.txt`/`points_imola.txt` (эти две — единственные трассы с
  bbox заметно больше остальных, см. ниже). Текстура снижена до
  `TRACK_FILL_CACHE_MAX_DIM`=2048px по большей стороне, но при близком зуме
  (`MAX_ZOOM`=2.5) на Монце это требовало Surface порядка 70000x80000px
  (~6.5 млрд пикселей, десятки ГБ) — раньше это не проявлялось, пока
  `MAX_ZOOM` не позволял так приблизиться, и на маленьких трассах, где сама
  текстура меньше экрана, масштабирование целиком было безопасно. Исправлено
  кадрированием текстуры по видимой на экране области МИРА (через
  `cam.screen_to_world`, переведённой в пиксели текстуры той же линейной
  калибровкой, что при постройке текстуры) — `Surface.subsurface` ДО
  `transform.scale`, а не после: результат масштабирования теперь всегда
  ограничен размером видимой области (`logical_width x logical_height` —
  ПОСЛЕ переезда панели в браузер это весь холст целиком, см. `Camera`
  ниже; раньше, когда камера смотрела только на `screen_width x
  screen_height`, было ограничено этим) независимо от zoom и размера
  трассы, потому что экран физически не может показать больше пикселей, чем
  в нём самом. Кэш результата по zoom стал не
  нужен — сама операция уже ограничена по стоимости размером экрана на
  каждый кадр (тот же порядок, что у `_grass_texture`, который и так
  блитится каждый кадр без кэша результата).
  Итоговый прирост стоимости кадра на `points_monza.txt` — от текстур/блитов
  выше, не от заливки полигона — профилирован в ~+19-40% к `draw_track()`
  (до введения кадрирования выше; зависело от того, менялся ли zoom в этом
  кадре); (3) декоративные бело-красные "шашечки" поперёк стартовой линии
  (`_draw_start_checkers`) — считаются ТОЛЬКО по `start_line` (2 точки), не по
  всей границе трассы, поэтому дёшевы независимо от размера трассы. Линии
  чекпоинтов (`CHECKPOINT_COLOR`) гейтятся `self.show_track_lines`
  (тогл "Show Track Lines" в UI-панели, см. ниже) — контур трассы и
  старт/финиш остаются видимыми ВСЕГДА, независимо от тогла.

- `car_racer/dashboard/` — браузерная панель мониторинга/управления, целиком
  на stdlib (без websocket-библиотек — сознательный выбор, тот же дух, что и
  отказ от `shapely` для сенсоров: не тянуть тяжёлые зависимости туда, где
  без них можно обойтись). Разделена на три файла:
  - `__init__.py` — состояние и обмен между главным потоком (pygame, где
    крутится `neat_runner/main.py`) и потоком HTTP-сервера: `_current`
    (dict, снимок "сейчас", целиком заменяется `set_current()`) и `_history`
    (list, по записи на завершённое поколение, добавляется
    `record_generation()`) читает-пишет ГЛАВНЫЙ поток, `snapshot()` отдаёт их
    копию — читает ПОТОК СЕРВЕРА по HTTP; `_commands` (`queue.Queue`) —
    наоборот, пишет поток сервера (`post_command()`, из `POST /api/command`),
    читает главный поток (`next_command()`, вызывается КАЖДЫЙ тик из
    `_handle_dashboard_commands`, см. `main.py` выше). Всё под общим
    `threading.Lock`, КРОМЕ `_commands` (у неё своя внутренняя блокировка
    `queue.Queue`). ВАЖНО: поток сервера НИКОГДА не трогает `pygame`/
    `pymunk`/`screen`/`panel` напрямую — только эти три структуры данных;
    вся реальная работа (мутация `physic_car.*`, `screen.load_track`,
    `RestartTrainingRequested` и т.п.) происходит в главном потоке при
    разборе команды, а не в обработчике HTTP-запроса. `serialize_genome`
    раскладывает геном в JSON (узлы с нормализованными x/y в `[0,1]` —
    входы слева, выходы справа, скрытые по топологическому уровню, как у
    `Screen.draw_network`) для отрисовки сети в браузере на `<canvas>`.
  - `server.py` — `http.server.ThreadingHTTPServer` на `127.0.0.1` (НЕ
    наружу) в daemon-потоке (не мешает тренировке, завершается вместе с
    процессом, не роняет её, если порт занят — `start_server()` просто
    печатает предупреждение и не поднимает сервер). `GET /api/stats` отдаёт
    `dashboard.snapshot()`, `POST /api/command` кладёт JSON-тело в очередь
    команд, всё остальное — статика из `web/` (с проверкой, что
    нормализованный путь не убегает за пределы `WEB_DIR` — простая защита от
    `..`-обхода каталога, сервер слушает только localhost, но раздача файлов
    всё равно не должна выходить за `web/`).
  - `web/{index.html,app.js,style.css}` — сам фронтенд (без сборки, чистые
    файлы, Chart.js с CDN для графиков). `app.js` опрашивает `/api/stats` раз
    в секунду (`POLL_MS`) и шлёт команды через `POST /api/command` по имени
    действия (`toggle_pause`/`set_grip`/`set_track`/... — имена ДОЛЖНЫ
    совпадать с `action ==` в `_handle_dashboard_commands`, см. `main.py`
    выше, единой схемы/enum на оба конца нет, синхронизировать вручную при
    добавлении новых команд). Поля инпутов не перезаписываются во время
    редактирования (`document.activeElement !== el` в `syncInputs`) — иначе
    полученный раз в секунду снимок сбрасывал бы то, что пользователь ещё
    печатает. `show_sensors`/`show_genome` (тогглы игрового окна, см.
    `UIPanel` выше) НЕ управляются из браузера — команды `set_show_sensors`/
    `set_show_genome` есть в `_handle_dashboard_commands`, но текущий
    `app.js` их нигде не вызывает (мёртвый путь с этой стороны, не баг).
  Известный пробел: `car_racer/config/error.log` (пишется `main.py` при
  крахе, см. выше) пока не добавлен в `.gitignore`.

  - `points.txt` (нарисована мышью) — геометрически отмасштабирована
    множителем `SCALE_FACTOR=2.0` (`rescale_legacy_tracks.py`, от левого
    верхнего угла bbox трассы, чтобы не уйти в отрицательные координаты) так,
    чтобы вместе с `PX_PER_METER=20` длина центральной линии стала
    правдоподобной для небольшого картинг-круга (~226-482 м — диапазон
    остался от эпохи, когда в эту группу входило больше трасс, см. ниже).
    `MAX_CHECKPOINT_GAP` (`file_manager/file_worker.py`, было 250px) и
    `SENSOR_RANGE` (`constants.py`, было 500px) удвоены СИНХРОННО с этим же
    множителем — иначе плотность чекпоинтов/дальность сенсоров относительно
    новой длины трассы изменилась бы вдвое, чего не было целью.
    `points_reserve.txt`/`points_reserve2.txt` (были в этой же группе) и
    `points_stadium_chicane.txt` (была в группе `track_builder`, ниже)
    удалены по запросу пользователя — их геометрия была признана
    неудачной/"кривой", отдельной замены не появилось.
  - `points_oval_half_mile.txt` (переименована из `points_oval.txt` -
    название теперь отражает реальный прототип) — пересобрана С НУЛЯ (не
    через `SCALE_FACTOR` выше) напрямую под реальные размеры короткого
    овального трека: радиус поворота 50м, прямые 250м, ширина полотна 12м
    (типичная для short-track) — итоговая длина круга ~814м (0.506 мили,
    класс "half-mile oval", известный типоразмер коротких овалов). Старая
    версия (через `OVAL_SCHEMA` в `track_builder.py` + `SCALE_FACTOR=2.0`,
    ширина 280px против радиуса 400px) выглядела заметно "квадратной" на
    внутренней границе (не баг в `offset_polyline`, а следствие того, что
    ширина полотна была слишком велика относительно радиуса поворота);
    при заметно большем радиусе (1000px) относительно ширины (240px) то же
    геометрическое смещение границ выглядит гладким/круглым с обеих сторон.
    `OVAL_SCHEMA` в `track_builder.py` больше НЕ используется для генерации
    актуального файла (оставлена как справочный пример формата схемы, у
    `track_builder.py` больше нет `__main__`, см. начало файла) — сам файл
    пересобирается вручную под нужные метры/`PX_PER_METER`.
  - `points_xti_winter.txt` — калибруется по-другому: у неё есть настоящая
    ground truth длины (1250 м, `REAL_LENGTH_M`), поэтому `draw_scale`
    (SVG-единица → px) подбирается напрямую из `PX_PER_METER`

    произвольный `TARGET_BBOX_PX` ("влезть в экран 2000x1200", актуальный
    только пока `check_collision_with_track` сверялся с
    `screen.screen_width/screen_height` — см. выше, эта причина больше не
    существует). Результат — бОльшая трасса (bbox ~6400x3250px вместо
    ~1680x850px, центральная линия ~25000px = 1250м×20px/м) — это ОЖИДАЕМО,
    не повод уменьшать масштаб обратно. `SENSOR_RANGE`/`MAX_CHECKPOINT_GAP`
    для неё СОЗНАТЕЛЬНО не подгонялись отдельно — она и раньше была "не как
    остальные" по масштабу, а единый глобальный `SENSOR_RANGE` физически не
    может одновременно быть "правильным" и для реально откалиброванной
    трассы, и для пяти без калибровки — принятое, не устраняемое здесь
    несоответствие.
  - `points_monza.txt`/`points_imola.txt` — НАСТОЯЩАЯ геометрия (не
    стилизованное приближение по схеме, как была первая версия — пользователь
    справедливо заметил, что не похоже; см. `car_racer/tracks/build_real_circuits.py`),
    оцифрована из двух реальных схем, положенных в корень репозитория:
    - Монца (`RaceCircuitAutodromaDiMonza.svg`) — НАСТОЯЩИЙ векторный SVG,
      один замкнутый `<path>` (это ЦЕНТРАЛЬНАЯ линия, не пара outer/inner) —
      парсится через `svgpathtools` (как `svg_track_importer.py`), дискретизируется
      равным шагом по длине дуги.
    - Имола (`Imola_2009.svg.webp`) — РАСТРОВОЕ изображение (несмотря на имя),
      векторных данных нет — центральная линия извлекается оцифровкой:
      альфа-композитинг на белый фон (ВАЖНО — картинка с прозрачным, не
      белым фоном; `.convert("L")` без композитинга красит весь прозрачный
      фон в чёрный, неотличимо от самой линии — так и произошло при первой
      попытке), бинаризация, выбор наибольшего компонента связности (кружки
      номеров поворотов/подписи — отдельные, не связанные с линией
      компоненты), ЗАМЫКАНИЕ (`ndimage.binary_closing`, 5 итераций) — линия
      трассы на этой картинке нарисована ДВОЙНОЙ (два очень близких
      параллельных контура), голая `skimage.morphology.skeletonize()` двух
      почти-параллельных линий даёт не простую петлю, а "лестницу" (мелкие
      циклы между контурами) — closing сливает узкий зазор в одну сплошную
      полосу ДО скелетизации, тогда skeleton проходит по её середине. Отдельно
      вручную вырезан (закрашен белым до бинаризации) шашечный флаг
      старт-финиша (координаты подобраны визуально под этот конкретный
      файл) — он нарисован ПРЯМО НА линии трассы и, будучи сплошным блоком,
      а не тонкой линией, ломает скелетизацию. Скелет трассируется в
      упорядоченную петлю greedy-обходом по ближайшему соседу, с итеративной
      обрезкой тупиковых точек (spur pruning) для остаточного шума.
    - Общий пайплайн (`build_from_centerline`) для обеих: старт-финиш — на
      середине самого длинного прямого участка центральной линии (переиспользует
      `svg_track_importer._find_longest_straight_index`, вызванный с одним и
      тем же массивом в роли и outer, и inner — тогда её `(outer+inner)/2`
      внутри возвращает саму центральную линию); смещение на половину реальной
      ширины (`track_builder.offset_polyline`) в обе стороны с проверкой по
      локальному радиусу кривизны (`CURVATURE_SAFETY_FACTOR`, как в
      `svg_track_importer.widen_boundaries`) — сужает ширину, если понадобится,
      не самопересекается; масштаб — `PX_PER_METER * (реальная_длина / длина_в_пикселях_исходника)`,
      как у `points_xti_winter.txt`. Реальные длина/ширина найдены в интернете
      (не выдуманы): Монца 5793м, ширина 10-12м (среднее 11м); Имола 4909м
      (современная конфигурация), ширина 14м. Обе сошлись в точную реальную
      длину (по построению калибровки), ширина не урезалась ни у одной.
      Проверено: ноль самопересечений, обе загружаются в `Screen`,
      headless-симуляция группы машин не падает, видны в dropdown,
      `.ideal_line.json`/`self_check()` проходят, визуально узнаваемы (боот-образная
      Имола, характерная трапеция Монцы) — сравнивались со схемами-референсами.

    bbox этих двух трасс (~29000x33000px у Монцы, ~36600x19300px у Имолы) —
    ЗНАЧИТЕЛЬНО больше, чем у `points_xti_winter.txt` (~6400x3250px), под
    которую был откалиброван `MIN_ZOOM=0.25` (`car_racer/screen/camera.py`):
    на 0.25 видимый кусок мира (viewport/zoom = 8000x4800px) оказывался
    ЦЕЛИКОМ внутри пустой середины кольца Монцы/Имолы — ни одной стены не
    видно, экран выглядел полностью чёрным при автоматическом
    `Screen.compute_fit_zoom()` (не баг рендера самих трасс — они рисуются
    нормально на любом зуме, где реально попадают в кадр). Понижен до
    `MIN_ZOOM=0.02` (видимый кусок ~100000x60000px — с запасом вписывает
    Монцу целиком).
- `car_racer/checkpoints/checkpoints/*.pkl` — чекпоинты обучения (весь

- `car_racer/config/config-feedforward.txt` — конфиг топологии/мутаций NEAT

## Важные соглашения

- Все входы нейросети нормализованы примерно в `[-1, 1]` / `[0, 1]`.
  Максимальная дальность луча-сенсора — константа `SENSOR_RANGE` в
  `car_racer/constants.py` (сейчас 1000px, было 500 — см. раздел про
  масштаб треков ниже); при отсутствии пересечения луча со стеной
  подставляется `SENSOR_RANGE`, а не `inf` (важно: `inf` как вход сети ранее
  был багом, который мог портить веса генома).
- Чекпоинты на трассе (`screen.checkpoints_lines`) должны проходиться строго
  по порядку — у машины есть счётчик `next_checkpoint_index`, а не список
  "уже пройденных в любом порядке".
- Формат файла трассы: строка 1 — внешняя граница, строка 2 — внутренняя,
  далее N−1 строк — чекпоинты (пары точек), последняя строка — линия старта
  (см. `file_manager/file_worker.parse_track`). `parse_track` дополнительно
  ПРОГОНЯЕТ чекпоинты через `_densify_checkpoints` (`MAX_CHECKPOINT_GAP`,
  сейчас 2200px, было 500 — см. раздел про масштаб треков ниже): если
  середины двух соседних чекпоинтов дальше друг от друга
  чем порог, между ними линейно интерполируются дополнительные — на
  нарисованных мышью треках пара соседних чекпоинтов может оказаться в разы
  дальше друг от друга, чем остальные (см. `points.txt`), и машина не
  получает вообще никакого фитнес-сигнала на этом отрезке. Это чисто
  геометрическое приближение (не следует изгибу трассы), но применяется
  прозрачно для остального кода — `screen.checkpoints_lines` уже содержит
  плотный список, файлы трасс на диске не трогаются.

  Количество чекпоинтов на ВСЕХ трассах снижено ~3-4x по явному запросу
  пользователя (после того как компас — `_heading_error_to_next_checkpoint`
  — стал давать постоянный сглаженный направляющий сигнал, необходимость в
  очень частых чекпоинтах для фитнеса снизилась). Два разных механизма (какой
  сработал — зависит от того, КАК изначально генерировалась трасса):
  - `points.txt`/`points_oval_half_mile.txt`/`points_xti_winter.txt` — их
    чекпоинты и раньше генерировались С ШАГОМ УЖЕ МЕНЬШЕ порога
    `MAX_CHECKPOINT_GAP` (т.е. `_densify_checkpoints` для них не
    добавляла ничего сверху) — подъём порога сам по себе ничего не изменил,
    пришлось вручную прорядить САМ файл (оставлен каждый 4-й чекпоинт,
    последний перед финишем всегда сохраняется, чтобы не остался большой
    разрыв перед стартовой линией).
  - `points_monza.txt`/`points_imola.txt` — наоборот, генерировались с шагом
    ~1200px (60м, см. `build_real_circuits.py`) — БОЛЬШЕ старого порога
    500px, из-за чего `_densify_checkpoints` парадоксально ВТРОЕ увеличивала
    их количество сверх задуманного (267/227 вместо 89/68) - подъём порога
    до 2200 (выше и этого шага, и максимального разрыва после прореживания
    остальных трёх трасс) убрал это автодоуплотнение, файлы самих трасс не
    трогались.
- Сенсоры считают пересечение лучей со стенами через `helpers.calculate.cast_ray`
  (ручной векторизованный numpy-рейкастинг), не через `shapely` — `shapely`
  убран из зависимостей. Не добавляй его обратно ради удобства intersection-API:
  это было главным узким местом производительности (создание Python-объектов
  геометрии на каждый сегмент трассы на каждый луч на каждую машину на каждый
  тик).
- `helpers.calculate.build_track_segments` (собирает `track_outer`/`track_inner`
  в пары точек-сегментов для `cast_ray`/`min_distance_to_segments`) ЗАМЫКАЕТ
  контур — сегмент "последняя точка → первая" создаётся всегда
  (`starts[i], ends[(i+1) % n]`). Раньше было `range(len(line) - 1)`, то есть
  этот сегмент НЕ создавался — на трассах, где первая и последняя точки
  контура не совпадают вплотную (координаты трасс, нарисованных мышью или
  оцифрованных из реальных схем, почти никогда не сходятся идеально:
  `points.txt` — разрыв ~10px, `points_monza.txt` — ~128px), в стене
  оставалась настоящая ДЫРА на стыке — ни сенсоры, ни `check_collision_with_track`
  не видели там стену вообще, машина могла проехать сквозь неё без всякого
  столкновения. Файлы трасс на диске не трогаются — `track_outer`/`track_inner`
  как были без явно продублированной первой/последней точки, так и остались,
  замыкание чисто в сборке сегментов.
