# CLAUDE.md

Гоночная игра на pygame + pymunk, где машинка учится проходить трассу через
нейроэволюцию (`neat-python`). Подробное описание — в [README.md](README.md).

## Запуск — всегда из корня репозитория, через `-m`

```bash
python -m car_racer.neat_runner.main   # обучение NEAT (основной режим)
python -m car_racer.runner.main        # ручное управление (стрелки)
python -m helpers.draw_track           # конструктор трассы мышью
python -m car_racer.tracks.build_real_circuits    # оцифровывает Монцу/Имолу из реальных схем
```

`car_racer/tracks/track_builder.py` — библиотека для генерации по схеме
(`build_track`/`fit_to_screen`/`save_track_file`, см. ниже), у неё больше НЕТ
`__main__` (раньше генерировала `points_oval.txt`/`points_stadium_chicane.txt`
— первый пересобран отдельно под реальные метры, второй удалён — оставлять
исполняемый пример, воскрешающий их под старыми именами, было бы только
путаницей). `OVAL_SCHEMA`/`STADIUM_WITH_CHICANE_SCHEMA` внутри — просто
справочные примеры формата схемы, не генерируют файлы сами по себе.

Код использует относительные пути (`./assets/car.png`, `car_racer/tracks/...`)
и абсолютные импорты `from car_racer.xxx import ...` / `from helpers.xxx import ...`.
Запуск файла напрямую (`python car_racer/neat_runner/main.py`) или не из корня
репозитория сломает и то, и другое — только `-m` из корня.

## Окружение

venv в `.venv/`, зависимости в `requirements.txt` — версии актуальные на
момент написания. `pymunk` (7.x) и `neat-python` (2.0) в последних мажорных
релизах ломают обратную совместимость (у pymunk переписан `Vec2d` и другое
поведение `pygame_util`, у neat-python несовместимый формат чекпоинтов и
новые обязательные параметры конфига) — это проверено и учтено (см.
комментарии в `requirements.txt` и правки в `config-feedforward.txt`), но при
следующем мажорном апгрейде любой из зависимостей повторяй ту же процедуру:
проверяй changelog на breaking changes и прогоняй реальный тик игры (создание
`Screen`/`GameEnvironment`, `env.update()` в цикле) headless
(`SDL_VIDEODRIVER=dummy`) перед тем как менять версию в `requirements.txt`.
Чекпоинты обучения в `car_racer/checkpoints/` — расходный материал, их не
жалко терять при смене версии neat-python (несовместимы между мажорными
версиями) или в принципе когда они не нужны.

## Архитектура

- `car_racer/constants.py` — `PX_PER_METER = 20.0` (`METERS_PER_PX` — обратная
  величина) — единственная РЕАЛЬНАЯ калибровка px→метры в проекте (раньше её
  не было вообще, см. про `GRIP_ACCEL_PER_G`/`ENGINE_POWER_HP` ниже — те
  давно были УСЛОВНЫМИ этикетками, не калибровкой длины). Привязана к
  спрайту тренировочной машины (`PhyCar(..., car_size=(15, 35), ...)` в
  `neat_runner/game_instatnse.py`) — 15px ширины = 0.75 м, 35px длины = 1.75 м
  (правдоподобный прокатный картинг), отсюда `20.0`. Используется ТОЛЬКО для
  геометрии/визуализации (масштаб трасс, масштабная линейка — см.
  `Screen.draw_scale_bar` ниже; той же конвертацией `ui_panel.py` переводит
  "Max Distance" в статистике из игровых px в метры при выводе - сам
  `max_distance` в `neat_runner/main.py` остаётся в px, делится на
  `PX_PER_METER` только в строке для отображения) — физика машины (`MAX_SPEED`, `GRIP_ACCEL`,
  `ENGINE_POWER_HP`, `ROTATE_POWER` и т.п. в `physic_car.py`) в игровых
  px/с, px/с² не тронута и не привязана к этому масштабу.
- `car_racer/cars/{abs_car,physic_car,simplecar}.py` — модели машины.
  `PhyCar` (физика pymunk) — используется в обучении и как основная модель.
  `SimpleCar` (упрощённая кинематика) — для ручного режима, БЕЗ модели
  сцепления ниже (не используется в обучении, трогать не стали). Они почти
  1:1 дублируют друг друга (`get_inputs_for_network`, `check_collision_with_*`)
  — известный технический долг, а не недосмотр; при правках сенсоров/
  чекпоинтов меняй оба класса синхронно.
  `PhyCar.throttle()`/`turn()` не мутируют тело напрямую — они только
  запоминают запрошенное действие (`_pending_throttle_power`/`_pending_turn_power`
  + флаги `_has_pending_*`), а `update()` применяет их СОВМЕСТНО через
  `_apply_controls()` — "круг трения" (`GRIP_ACCEL`): сумма продольного
  (газ/тормоз) и поперечного (руль, `v*ω`) ускорения ограничена одним общим
  бюджетом, нельзя одновременно жать газ в пол и резко поворачивать на
  пределе. Плюс штраф на руль на низкой скорости (`NO_DIFF_*`) — приближение
  картинга без дифференциала (спул), у которого крутые повороты на малом ходу
  даются хуже. Поверх круга трения — три эффекта на РЕЗКИЕ (не просто
  сильные) воздействия, все в `_apply_controls`/`_desired_angular_velocity`:
  снос (`UNDERSTEER_*` — резкий скачок руля за тик снижает эффективность
  поворота именно на этот тик), занос (`OVERSTEER_*` — резкий скачок газа
  при уже ненулевой угловой скорости добавляет лишнее вращение В ТУ ЖЕ
  сторону, НЕ ограничено `GRIP_ACCEL` — это потеря сцепления, а не манёвр в
  его пределах, только общий потолок `ROTATE_POWER`; гейтится
  `OVERSTEER_MIN_ANGULAR`, чтобы резкий старт с места не давал случайный
  спин), скраб (`STEER_SCRUB_COEFF` — поворот сам по себе гасит скорость
  даже в пределах бюджета сцепления, не только на его пределе). Все три
  реагируют на `|Δ(throttle_power/turn_power)|` между тиками — для этого
  `PhyCar` хранит `_prev_throttle_power`/`_prev_turn_power`, обновляются в
  конце `_apply_controls()` только если соответствующий `_has_pending_*` был
  True в этот тик. Если ни throttle(), ни turn() не вызывались в этом тике
  (ручной режим при отпущенных клавишах — там рулит `damping()`) —
  `_apply_controls()` не вызывается вовсе, поведение `damping()` не трогается.
  Эта физика меняет ощущение вождения и фитнес-сигнал заметно — старые
  чекпоинты обучения технически загрузятся (структура генома не изменилась),
  но были натренированы под старую (не связанную газ/руль) физику.
  `GRIP_ACCEL`, `CAR_MASS`, `ENGINE_POWER_HP` — модульные переменные (не
  константы в привычном смысле): UI-панель (`ui_panel.py`, поля "Сцепление
  (g)"/"Вес (кг)"/"Мощность (л.с.)") мутирует их напрямую через
  `car_racer.cars.physic_car.<ИМЯ> = ...` из `neat_runner/main.py` — новое
  значение подхватывают только НОВЫЕ машины (следующая группа), у уже бегущих
  ничего не меняется на лету. Конвертация из наглядных единиц UI в игровые —
  через `GRIP_ACCEL_PER_G`/`REFERENCE_MASS_KG`/`REFERENCE_POWER_HP` (см.
  комментарии в `physic_car.py`) — это калибровочные ЭТИКЕТКИ для слайдеров,
  а не независимая физическая калибровка px→метры (её как не было, так и нет).
  `check_collision_with_track` считает расстояние до стен векторизованно
  (`helpers.calculate.min_distance_to_segments`, те же `track_segments_start/end`,
  что и сенсоры) — раньше был Python-цикл с `pygame.Rect.clipline()` по
  каждому сегменту + повторное чтение `body.position` внутри цикла, что после
  удаления `shapely` из сенсоров стало ~74% времени тика (профилировано);
  сейчас общий прирост на этом месте — ~5.5x. Перед этой проверкой — ВТОРОЙ,
  грубый backstop-барьер: позиция машины сравнивается с `screen.world_bounds`
  (`(min_x, min_y, max_x, max_y)`, см. `Screen._recompute_world_bounds`) —
  bounding box ТЕКУЩЕЙ трассы (`track_outer`+`track_inner`) плюс отступ
  `WORLD_BOUNDS_MARGIN`=200px. Раньше здесь были фиксированные
  `screen.screen_width/screen.screen_height` (2000x1200) — перестало
  работать, когда трасса стала физически больше рендер-канваса (см.
  `points_xti_winter.txt` ниже, bbox ~6400x3250px) — со старой проверкой
  машины на дальней части такой трассы ложно считались бы выехавшими за
  пределы. `world_bounds` — ЧИСТО числовой прямоугольник (4 float на
  сравнение позиции), НЕ связан с размером `self.win`/`Camera`-viewport —
  рендер-канвас (~2000x1200) не меняется вместе с размером мира, в этом и
  смысл `Camera` (пан+зум показывает произвольно большой мир на канвасе
  фиксированного размера). Это ВТОРИЧНЫЙ барьер ("машина где-то ДАЛЕКО за
  пределами трассы") — основной детектор "разбился о стену" остаётся
  `min_distance_to_segments` и не связан с `world_bounds` вообще.
  `SimpleCar.check_collision_with_track` — синхронно то же самое (см. общее
  правило "меняй оба класса синхронно" выше).
- `car_racer/neat_runner/game_instatnse.py` (да, опечатка в имени файла — так
  сложилось исторически, менять не нужно без явной причины, на неё много
  ссылок) — одна "игровая сессия" генома, разделена на `decide()` (сенсоры →
  сеть → газ/руль, физику не шагает) и `resolve()` (вызывается ПОСЛЕ шага
  физики: бухгалтерия машины + проверка столкновений/чекпоинтов/фитнеса).
  Разделение существует ради общего `pymunk.Space` на группу — см. ниже.
  `update()` = `decide()+resolve()` одним вызовом, для одиночного
  использования без общего Space (тогда физику шагает сам `car.update()`).
  Инпуты сети — 10 нормализованных значений (угол/скорость + "компас" на
  следующий чекпоинт + 7 дистанций лучей-сенсоров), выходы — газ и руль
  подаются в машину напрямую, без порога/dead zone. Компас (см.
  `PhyCar._heading_error_to_next_checkpoint`/аналог в `SimpleCar`) добавлен
  после того, как долгий прогон (56 поколений, лучший фитнес в популяции всё
  время держался ~1.3-1.7, среднее не росло, видов — 1 всё время) показал,
  что чисто реактивных лучей-дальномеров недостаточно: без сигнала "куда
  едет трасса" сеть не может надёжно выбрать нужный поворот там, где стены
  не подсказывают его достаточно рано. Компас указывает НЕ точно на середину
  следующего чекпоинта, а на взвешенную смесь (`CHECKPOINT_LOOKAHEAD_WEIGHT`
  в `physic_car.py`, сейчас 0.6/0.4) середины следующего чекпоинта и того,
  что идёт ЗА ним (`_gate_midpoint`) — точное прицеливание в один чекпоинт
  при плотных чекпоинтах (см. `_densify_checkpoints`) давало заметный
  зигзаг вокруг сглаженной трассы (пользователь принял это за "тягу к
  идеальной линии" — на деле `ideal_line` в фитнес/сеть вообще не подключена,
  только визуальный оверлей и статистика "Ideal lap" в панели). Полностью
  убирать компас не стали — риск вернуть застревание обучения, которое он и
  решал (см. абзац выше); сглаживание цели даёт направляющий сигнал без
  дословного "от точки к точке". Меняет число входов сети
  (`num_inputs` в `config-feedforward.txt`) — старые чекпоинты обучения
  структурно несовместимы, но они и так расходный материал (см. раздел
  "Окружение"). Таймаут и время круга считаются в тиках (`ticks_elapsed`,
  `TICK_RATE` в `car_racer/constants.py`), не в `time.time()` — важно не
  откатывать на wall-clock, иначе сломается турбо-режим (см. ниже).
- `car_racer/neat_runner/main.py` — цикл эволюции: геномы группами по
  `GROUP_SIZE`, чекпоинт всей популяции сохраняется через `pickle` после
  каждого поколения (не через встроенный `neat.Checkpointer`). Все машины
  группы делят один `pymunk.Space` (создаётся заново на каждую попытку
  группы) — порядок в тик-цикле строго `decide() для всех → space.step() один
  раз → resolve() для всех`; не вызывай `env.update()` напрямую в групповом
  цикле, это заново создаст собственный Space внутри PhyCar и сломает шаринг.
  `Screen`/`UIPanel` создаются один раз (модульная переменная `screen`,
  лениво инициализируется при первом вызове `eval_genomes`) и переиспользуются
  между поколениями — не пересоздавай их каждый вызов, иначе слетит состояние
  панели (пауза/Unlimited FPS) и будет пересоздаваться окно.
  Ручное панорамирование камеры (drag ЛКМ по игровому полю, как на карте) —
  модульные `_camera_drag_active`/`_camera_drag_last_pos`/`_camera_manual_pan`,
  обрабатывается в том же `for event in pygame.event.get():`, что и
  `VIDEORESIZE`/клики панели (событие уже переведено в логические координаты
  холста через `screen.window_to_logical` — переиспользует то же
  преобразование, что и клики по панели). `MOUSEBUTTONDOWN` с `event.pos[0] <
  screen.screen_width` (не по панели справа) и не "съеденный" `panel.handle_event`
  начинает драг; `MOUSEMOTION` двигает `camera.center` на дельту мыши,
  делённую на `camera.zoom`, в СЕТЕВОМ направлении (карта едет ВМЕСТЕ с
  курсором). Независимо от Camera Follow, но координируется с ним:
  `_camera_drag_active` (True только пока зажата ЛКМ) подавляет
  `camera.follow(...)` в рендер-блоке на время самого драга — иначе follow
  затирал бы драг в тот же кадр; отпустили ЛКМ — follow как обычно продолжает
  центрировать камеру на лидере со следующего кадра (драг "временно
  перекрывает" follow, а не отключает его). `_camera_manual_pan` (True после
  ПЕРВОГО же драга, не сбрасывается по отпусканию ЛКМ) подавляет
  `center_on_field(...)` в режиме "Camera Follow выключен" — без этого ручной
  пан отменялся бы на следующем же отрисованном кадре (`center_on_field`
  вызывается там каждый кадр). Оба флага сбрасываются при смене трассы
  (`consume_track_change`) — координаты новой трассы не связаны со старой
  панорамой.
  Зум колесом мыши — `MOUSEWHEEL` в том же цикле событий: умножает
  `panel.zoom` на `1.15**event.y` (мультипликативный шаг — одинаково заметен
  и у минимального, и у максимального zoom), явно зажимает результат в
  `[MIN_ZOOM, MAX_ZOOM]` (`car_racer/screen/camera.py`) ПЕРЕД
  `panel.sync_initial_values(zoom=...)` — сам `sync_initial_values` зажимает
  только `zoom_slider.value`, а не `panel.zoom` (простое поле, читается прямо
  в `screen.camera.zoom = panel.zoom` в рендер-блоке), так что без явного
  клампа здесь многократный скролл в одну сторону увёл бы zoom за пределы,
  которые слайдер мышью и так не позволяет достичь. Активен только когда
  курсор (переведённый в логические координаты) над игровым полем, не
  панелью.
  Автоматический "показать всю трассу" зум — `Screen.compute_fit_zoom()`
  подбирает zoom, при котором bounding box трассы (`_track_bbox_size`, см.
  `_recompute_world_bounds`) занимает `fill_fraction`=92% игрового поля
  (`screen_width x screen_height`), зажат в `[MIN_ZOOM, MAX_ZOOM]`.
  `neat_runner/main.py` применяет его как стартовый zoom при первом создании
  `screen`/`panel` И при каждой смене трассы (`consume_track_change`) —
  ИГНОРИРУЯ сохранённый в `user_settings.json` zoom (см. `settings_store.py`
  выше): при открытии окна трасса должна сразу заполнять экран, а не
  восстанавливать zoom прошлой сессии, подобранный под трассу совсем другого
  реального размера (диапазон между `points_oval_half_mile.txt` и
  `points_monza.txt` теперь огромный, см. `PX_PER_METER` выше).
- `car_racer/screen/screen.py` — окно/отрисовка трассы/визуализация сети.
  `Screen(track_file=...)` задаёт файл трассы, `screen.load_track(filename)`
  переключает трассу на лету (используется UI-панелью) — оба пути пересчитывают
  `track_segments_start/end` (numpy-кэш границ трассы для `cast_ray`) И
  `screen.world_bounds`/`screen.track_center` (`_recompute_world_bounds`) —
  не забывай вызывать оба пересчёта при любом другом способе поменять
  `track_outer/track_inner`. `track_center` — центр bounding box трассы (БЕЗ
  отступа) — нужен камере в режиме "показать весь трек" (см. `camera.py`
  ниже); раньше для этого использовался `(viewport_width/2, viewport_height/2)`,
  что совпадало с реальным центром трассы только пока все трассы были
  нарисованы внутри той же коробки, что и viewport (~2000x1200) — для трасс
  крупнее viewport'а (`points_xti_winter.txt`) это совпадение больше не
  работает.
  `Screen.draw_scale_bar()` — масштабная линейка google-maps-стиля в левом
  нижнем углу ИГРОВОГО ПОЛЯ (не в UI-панели справа — свойство камеры/карты, а
  не панели управления): брусок с засечками + подпись "N m"/"N km". Каждый
  кадр подбирает "круглое" число метров из ряда 1/2/5/10/20/50 м... такое,
  что его экранная длина при ТЕКУЩЕМ `camera.zoom` ближе всего к
  `SCALE_BAR_TARGET_PX`=110px — живо реагирует на слайдер Zoom без доп.
  действий. Перевод метры→экран идёт в два шага, по общей конвенции модуля:
  метры→мировые px (`* PX_PER_METER`, единственная калибровка px→метры в
  проекте) → экранные px (`camera.scale_length`, учитывает zoom). Вызывается
  из `neat_runner/main.py` рядом с `draw_track()`.
  `Screen.draw_track()` — раньше рисовал только контурные polyline outer/inner
  на сплошном чёрном (`self.win.fill(BLACK)`), полотно между ними и всё
  снаружи не заливались вовсе — выглядело пусто/безжизненно, особенно на
  крупных реальных трассах. Теперь: (1) фон снаружи — закэшированная один раз
  (`_build_grass_texture`, лениво при первом кадре) слегка "мятая" зелёная
  текстура (`GRASS_GREEN` + numpy-шум по блокам `GRASS_NOISE_SCALE`px,
  растянутый `smoothscale` до размера игрового поля) — просто блитится каждый
  кадр В ЭКРАННЫХ координатах (НЕ едет с камерой при пане/зуме — осознанный
  компромисс простоты/производительности, это фон, не часть трассы);
  (2) само полотно (кольцо между outer/inner) — тёмно-серый `ASPHALT_COLOR`
  из ОТДЕЛЬНОЙ закэшированной текстуры В МИРОВЫХ координатах
  (`_build_track_fill_texture`/`_draw_track_fill`) — залить `pygame.draw.polygon`
  по ПОЛНЫМ outer/inner В ЭКРАННЫХ координатах КАЖДЫЙ КАДР стоило ~18ms/кадр
  на `points_monza.txt` (~9700 точек полотна, полигон в pygame стоит от числа
  вершин) — вместо этого полигон заливается ОДИН РАЗ в свою текстуру
  (пониженное разрешение, `TRACK_FILL_CACHE_MAX_DIM`=2048px по большей
  стороне bbox трассы), а каждый кадр эта готовая Surface просто
  масштабируется (`pygame.transform.scale`) под текущий `cam.zoom` и блитится
  в `cam.world_to_screen(origin)` — корректно ТОЛЬКО потому что `Camera` строго
  аффинна (scale+translate, без поворота, см. `camera.py`), так что
  "перемасштабировать готовую картинку" эквивалентно "перерисовать полигон
  под новую камеру". Плюс кэш РЕЗУЛЬТАТА `transform.scale` под последний
  `cam.zoom` (`_track_fill_scaled_cache`) — zoom обычно стабилен между кадрами
  (слайдер/колесо мыши двигают редко), а `cam.center` меняется почти всегда
  (Camera Follow) — так что дорогой resize пересчитывается только при
  реальном изменении zoom, а не на каждый кадр. Оба кэша инвалидируются в
  `load_track()` (новая трасса — новый bbox/полигон). ВАЖНО: имя поля
  `track_outer` НЕ гарантирует, что этот контур геометрически больше
  `track_inner` (на `points_oval_half_mile.txt` наоборот) — `_build_track_fill_texture`
  сравнивает площади (`_polygon_area`, шоеласа) и большим контуром всегда
  заливает АСФАЛЬТ первым, меньшим — "дырку" (цветом фона, БЕЗ шума текстуры —
  видимый шов почти не заметен, сразу перекрывается чёткой контурной линией
  outer/inner, рисуемой отдельно по полным координатам); залить не глядя по
  порядку полей — типичный способ получить полностью невидимое полотно.
  Итоговый прирост стоимости кадра на `points_monza.txt` — от текстур/блитов
  выше, не от заливки полигона — профилирован в ~+19-40% к `draw_track()`
  (зависит от того, меняется ли zoom в этом кадре, см. `_track_fill_scaled_cache`
  выше); (3) декоративные бело-красные "шашечки" поперёк стартовой линии
  (`_draw_start_checkers`) — считаются ТОЛЬКО по `start_line` (2 точки), не по
  всей границе трассы, поэтому дёшевы независимо от размера трассы. Линии
  чекпоинтов (`CHECKPOINT_COLOR`) гейтятся `self.show_track_lines`
  (тогл "Show Track Lines" в UI-панели, см. ниже) — контур трассы и
  старт/финиш остаются видимыми ВСЕГДА, независимо от тогла.

    оцифрована из двух реальных схем, положенных в корень репозитория:
    - Монца (`RaceCircuitAutodromaDiMonza.svg`) — НАСТОЯЩИЙ векторный SVG,
      один замкнутый `<path>` (это ЦЕНТРАЛЬНАЯ линия, не пара outer/inner) —
      парсится через `svgpathtools` (как `svg_track_importer.py`), дискретизируется
      равным шагом по длине дуги.
    - Имола (`Imola_2009.svg.webp`) — РАСТРОВОЕ изображение (несмотря на имя),
      векторных данных нет — центральная линия извлекается оцифровкой:
      альфа-композитинг на белый фон (ВАЖНО — картинка с прозрачным, не
      белым фоном; `.convert("L")` без композитинга красит весь прозрачный
      фон в чёрный, неотличимо от самой линии — так и произошло при первой
      попытке), бинаризация, выбор наибольшего компонента связности (кружки
      номеров поворотов/подписи — отдельные, не связанные с линией
      компоненты), ЗАМЫКАНИЕ (`ndimage.binary_closing`, 5 итераций) — линия
      трассы на этой картинке нарисована ДВОЙНОЙ (два очень близких
      параллельных контура), голая `skimage.morphology.skeletonize()` двух
      почти-параллельных линий даёт не простую петлю, а "лестницу" (мелкие
      циклы между контурами) — closing сливает узкий зазор в одну сплошную
      полосу ДО скелетизации, тогда skeleton проходит по её середине. Отдельно
      вручную вырезан (закрашен белым до бинаризации) шашечный флаг
      старт-финиша (координаты подобраны визуально под этот конкретный
      файл) — он нарисован ПРЯМО НА линии трассы и, будучи сплошным блоком,
      а не тонкой линией, ломает скелетизацию. Скелет трассируется в
      упорядоченную петлю greedy-обходом по ближайшему соседу, с итеративной
      обрезкой тупиковых точек (spur pruning) для остаточного шума.
    - Общий пайплайн (`build_from_centerline`) для обеих: старт-финиш — на
      середине самого длинного прямого участка центральной линии (переиспользует
      `svg_track_importer._find_longest_straight_index`, вызванный с одним и
      тем же массивом в роли и outer, и inner — тогда её `(outer+inner)/2`
      внутри возвращает саму центральную линию); смещение на половину реальной
      ширины (`track_builder.offset_polyline`) в обе стороны с проверкой по
      локальному радиусу кривизны (`CURVATURE_SAFETY_FACTOR`, как в
      `svg_track_importer.widen_boundaries`) — сужает ширину, если понадобится,
      не самопересекается; масштаб — `PX_PER_METER * (реальная_длина / длина_в_пикселях_исходника)`,
      как у `points_xti_winter.txt`. Реальные длина/ширина найдены в интернете
      (не выдуманы): Монца 5793м, ширина 10-12м (среднее 11м); Имола 4909м
      (современная конфигурация), ширина 14м. Обе сошлись в точную реальную
      длину (по построению калибровки), ширина не урезалась ни у одной.
      Проверено: ноль самопересечений, обе загружаются в `Screen`,
      headless-симуляция группы машин не падает, видны в dropdown,
      `.ideal_line.json`/`self_check()` проходят, визуально узнаваемы (боот-образная
      Имола, характерная трапеция Монцы) — сравнивались со схемами-референсами.

    bbox этих двух трасс (~29000x33000px у Монцы, ~36600x19300px у Имолы) —
    ЗНАЧИТЕЛЬНО больше, чем у `points_xti_winter.txt` (~6400x3250px), под
    которую был откалиброван `MIN_ZOOM=0.25` (`car_racer/screen/camera.py`):
    на 0.25 видимый кусок мира (viewport/zoom = 8000x4800px) оказывался
    ЦЕЛИКОМ внутри пустой середины кольца Монцы/Имолы — ни одной стены не
    видно, экран выглядел полностью чёрным при автоматическом
    `Screen.compute_fit_zoom()` (не баг рендера самих трасс — они рисуются
    нормально на любом зуме, где реально попадают в кадр). Понижен до
    `MIN_ZOOM=0.02` (видимый кусок ~100000x60000px — с запасом вписывает
    Монцу целиком).
- `car_racer/checkpoints/checkpoints/*.pkl` — чекпоинты обучения (весь
  `neat.Population` целиком), в git не хранятся, могут весить сотни МБ — ГБ.
- `car_racer/config/config-feedforward.txt` — конфиг топологии/мутаций NEAT
  (10 входов, 2 выхода).

## Важные соглашения

- Все входы нейросети нормализованы примерно в `[-1, 1]` / `[0, 1]`.
  Максимальная дальность луча-сенсора — константа `SENSOR_RANGE` в
  `car_racer/constants.py` (сейчас 1000px, было 500 — см. раздел про
  масштаб треков ниже); при отсутствии пересечения луча со стеной
  подставляется `SENSOR_RANGE`, а не `inf` (важно: `inf` как вход сети ранее
  был багом, который мог портить веса генома).
- Чекпоинты на трассе (`screen.checkpoints_lines`) должны проходиться строго
  по порядку — у машины есть счётчик `next_checkpoint_index`, а не список
  "уже пройденных в любом порядке".
- Формат файла трассы: строка 1 — внешняя граница, строка 2 — внутренняя,
  далее N−1 строк — чекпоинты (пары точек), последняя строка — линия старта
  (см. `file_manager/file_worker.parse_track`). `parse_track` дополнительно
  ПРОГОНЯЕТ чекпоинты через `_densify_checkpoints` (`MAX_CHECKPOINT_GAP`,
  сейчас 2200px, было 500 — см. раздел про масштаб треков ниже): если
  середины двух соседних чекпоинтов дальше друг от друга
  чем порог, между ними линейно интерполируются дополнительные — на
  нарисованных мышью треках пара соседних чекпоинтов может оказаться в разы
  дальше друг от друга, чем остальные (см. `points.txt`), и машина не
  получает вообще никакого фитнес-сигнала на этом отрезке. Это чисто
  геометрическое приближение (не следует изгибу трассы), но применяется
  прозрачно для остального кода — `screen.checkpoints_lines` уже содержит
  плотный список, файлы трасс на диске не трогаются.

  Количество чекпоинтов на ВСЕХ трассах снижено ~3-4x по явному запросу
  пользователя (после того как компас — `_heading_error_to_next_checkpoint`
  — стал давать постоянный сглаженный направляющий сигнал, необходимость в
  очень частых чекпоинтах для фитнеса снизилась). Два разных механизма (какой
  сработал — зависит от того, КАК изначально генерировалась трасса):
  - `points.txt`/`points_oval_half_mile.txt`/`points_xti_winter.txt` — их
    чекпоинты и раньше генерировались С ШАГОМ УЖЕ МЕНЬШЕ порога
    `MAX_CHECKPOINT_GAP` (т.е. `_densify_checkpoints` для них не
    добавляла ничего сверху) — подъём порога сам по себе ничего не изменил,
    пришлось вручную прорядить САМ файл (оставлен каждый 4-й чекпоинт,
    последний перед финишем всегда сохраняется, чтобы не остался большой
    разрыв перед стартовой линией).
  - `points_monza.txt`/`points_imola.txt` — наоборот, генерировались с шагом
    ~1200px (60м, см. `build_real_circuits.py`) — БОЛЬШЕ старого порога
    500px, из-за чего `_densify_checkpoints` парадоксально ВТРОЕ увеличивала
    их количество сверх задуманного (267/227 вместо 89/68) - подъём порога
    до 2200 (выше и этого шага, и максимального разрыва после прореживания
    остальных трёх трасс) убрал это автодоуплотнение, файлы самих трасс не
    трогались.
- Сенсоры считают пересечение лучей со стенами через `helpers.calculate.cast_ray`
  (ручной векторизованный numpy-рейкастинг), не через `shapely` — `shapely`
  убран из зависимостей. Не добавляй его обратно ради удобства intersection-API:
  это было главным узким местом производительности (создание Python-объектов
  геометрии на каждый сегмент трассы на каждый луч на каждую машину на каждый
  тик).
